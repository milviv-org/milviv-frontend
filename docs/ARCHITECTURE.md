# Архитектура MILVIV Frontend

Документ — источник правды о том, **как устроено приложение и почему**. Меняется вместе с кодом. Крупные решения дополнительно фиксируются в `docs/adr/` (Architecture Decision Records): одно решение — один файл, с контекстом и причинами. Через пять лет ADR отвечает на вопрос «почему так сделано», когда автор кода уже не помнит.

Связанные документы:
- [ROADMAP.md](ROADMAP.md) — этапы разработки.
- [DESIGN.md](DESIGN.md) — как получить дизайн и передать его в разработку.
- Продукт: `../milviv-org`. REST API: `../skyrim_grade_java/docs/rest-api`.

## 1. Принятые решения

| # | Решение | Почему |
|---|---------|--------|
| 1 | Vue 3 + TypeScript (strict) + Vite + Pinia + Vue Router | Базовый стек |
| 2 | **Feature-Sliced Design (FSD)**, упрощённый | Документированная методология с жёсткими правилами зависимостей; новый модуль добавляется без правки старых |
| 3 | **TanStack Query** для данных сервера, **Pinia** — только для клиентского состояния | Кеш, дедупликация запросов, отмена, фоновое обновление и инвалидация без своего кода |
| 4 | Свой HTTP-клиент на `fetch` | Нужны нестандартные вещи (single-flight refresh между вкладками); axios ничего не добавляет, кроме веса |
| 5 | Без UI-библиотек; headless-примитивы — только для сложной доступности (по согласованию) | Полный контроль над видом и весом |
| 6 | Дизайн-токены в CSS-переменных, светлая и тёмная темы | Тема меняется без перерисовки компонентов и без JS в рантайме |
| 7 | Только русский язык, **но** все доменные подписи (статусы, сложности, коды ошибок) — в словарях, не в шаблонах | Одно место правды для терминов; i18n при необходимости добавляется заменой словарей |
| 8 | Адаптивная вёрстка (mobile-first) + PWA | Решение анкеты |
| 9 | Явные импорты, **без** auto-import компонентов и API Vue | Читаемость и навигация по коду важнее экономии строк |
| 10 | Доменные события (типизированная шина) для побочных эффектов между модулями | Модули не знают друг о друге: «задача выполнена» → баланс, статистика, звук подписываются сами |

## 2. Слои (Feature-Sliced Design)

```
src/
├── app/        Инициализация: main.ts, провайдеры, роутер, layouts, глобальные стили
├── pages/      Страницы (маршруты). Тонкие: собирают виджеты и фичи
├── widgets/    Крупные самостоятельные блоки UI: боковое меню, календарь месяца, график статистики
├── features/   Действия пользователя: выполнить задачу, форма задачи, получить награду
├── entities/   Доменные сущности: task, project, goal, plan, reward, … (типы, API, запросы, базовый UI)
└── shared/     Не знает о домене: http-клиент, UI-kit, утилиты, конфиг
```

### Правило зависимостей (главное правило проекта)

Слой импортирует **только нижележащие** слои:

```
app → pages → widgets → features → entities → shared
```

- Слайсы одного слоя **не импортируют друг друга** (`features/complete-task` не знает о `features/redeem-reward`). Если нужно — общее опускается слоем ниже или связь идёт через доменные события.
- Каждый слайс имеет **публичный API** — `index.ts`. Импорт извне только через него: `@/entities/task`, никогда `@/entities/task/model/mappers`.
- Правила проверяет линтер (`eslint-plugin-boundaries`), а не память разработчика. Нарушение = красный CI.

Исключение, которое разрешаем осознанно: сущность может ссылаться на **тип** другой сущности через публичный API (`Task.projectId` — это строка, импорт не нужен; но если нужно — `import type`).

### Структура слайса

```
entities/task/
├── api/
│   ├── task.dto.ts        Типы ровно как в REST API (TaskDto, TaskInputDto)
│   ├── task.api.ts        Функции запросов: getTasks, getTask, createTask, …
│   └── task.queries.ts    Ключи кеша + useTasksQuery, useTaskQuery, мутации
├── model/
│   ├── task.types.ts      Доменная модель (Task) — то, с чем работает UI
│   ├── task.mappers.ts    DTO ⇄ модель, модель → тело PUT
│   └── task.rules.ts      Чистая доменная логика (isOverdue, canComplete)
├── ui/
│   └── TaskCard.vue       Отображение без действий
└── index.ts               Публичный API слайса
```

Слайсы проектируются под рост: в `model/` появится файл — внешние импорты не меняются.

### Карта слайсов

| Слой | Слайсы |
|------|--------|
| entities | `session`, `goal`, `project`, `task`, `plan`, `calendar`, `reflection`, `reward`, `points`, `statistics`, `sound-settings`, `ai-request`, `ai-memory` |

## 3. Работа с данными

### 3.1 Три вида состояния — три места хранения

| Вид | Пример | Где живёт |
|-----|--------|-----------|
| Серверное | задачи, баланс, статистика | TanStack Query (кеш) |
| Клиентское глобальное | текущий пользователь, тема, пароль скрытых наград | Pinia |
| Локальное UI | открыт ли диалог, значения формы | `ref` внутри компонента/композабла |
| URL | фильтры, страница, выбранный месяц | query-параметры роутера |

Главное правило: **серверные данные не копируются в Pinia**. Две копии одних данных рано или поздно расходятся.

### 3.2 HTTP-клиент (`shared/api`)

```
shared/api/
├── http-client.ts     request<T>(method, url, { body, query, headers, signal })
├── api-error.ts       class ApiError { status, code: ErrorCode, message, fieldErrors, retryAfter }
├── error-codes.ts     Перечень errorCode из API
├── auth-refresh.ts    Single-flight refresh (см. ниже)
└── index.ts
```

- `credentials: 'same-origin'`, JSON, `AbortSignal` (TanStack Query отменяет запросы ушедших со страницы компонентов).
- Любой не-2xx ответ превращается в `ApiError`. Код ниже по стеку работает с `error.code`, а не с HTTP-статусами.
- **Refresh токена** — самое хрупкое место, поэтому изолировано и покрыто тестами:
  1. Запрос получил `401` → клиент вызывает `refreshSession()` и повторяет запрос один раз.
  2. `refreshSession()` — single-flight: параллельные `401` внутри вкладки ждут один общий промис.
  3. Между вкладками — **Web Locks API** (`navigator.locks.request('milviv:refresh')`). Взяв лок, вкладка проверяет метку последнего refresh в `localStorage`: если другая вкладка уже обновила токен после начала нашего запроса — просто повторяем запрос без refresh. Так выполняется требование API «не вызывать refresh параллельно».
  4. Refresh вернул `401` → сессия завершена: событие `session:expired` → `BroadcastChannel` сообщает остальным вкладкам → редирект на `/login`.

### 3.3 Типы API, DTO и маппинг

OpenAPI у бэкенда нет, поэтому DTO пишутся вручную по `docs/rest-api` — **один файл DTO на сущность**, комментарий со ссылкой на раздел документации.

Маппер DTO → модель есть у каждой сущности, даже если сейчас он почти тождественный. Это граница: переименование поля в API правится в одном маппере, а не в 30 компонентах.

Даты:
- В модели даты остаются **ISO-строками** с брендированными типами `IsoDate` (`YYYY-MM-DD`) и `IsoDateTime`. Строки дешевле `Date`, сериализуемы, сравниваются без аллокаций.
- Вся работа с датами — только через `shared/lib/date`. В том числе `todayUtc()`, потому что сервер считает `overdue`, календарь и статистику по UTC. Прямой `new Date()` в компонентах запрещён договорённостью.

**PUT заменяет объект целиком** (непереданное поле очищается). Поэтому у каждой сущности есть маппер `toXxxInput(model)`, а формы всегда отправляют полный объект с `version`.

### 3.4 Запросы и кеш (TanStack Query)

Фабрика ключей на сущность — единственное место, где задаются ключи:

```ts
export const taskKeys = {
  all: ['tasks'] as const,
  lists: () => [...taskKeys.all, 'list'] as const,
  list: (f: TaskFilters) => [...taskKeys.lists(), f] as const,
  detail: (id: TaskId) => [...taskKeys.all, 'detail', id] as const,
}
```

- `staleTime` задаётся по сущности: справочники (вопросы рефлексии, настройки звуков) — минуты; задачи — десятки секунд. Без шторма повторных запросов при переходах.
- Пагинация — `useInfiniteQuery` (API отдаёт `limit/offset` без `total`: признак конца — пришло меньше `limit`).
- После мутации обновляем кеш точечно (`setQueryData` для detail из ответа) и инвалидируем списки.
- Оптимистичные обновления — только там, где откат очевиден (смена статуса). Создание и формы — без оптимизма.

### 3.5 Доменные события — связи между модулями

Выполнение задачи затрагивает баланс, статистику, календарь, сложность проекта, прогресс цели и звук. Если каждая мутация будет знать обо всех потребителях, получится паутина. Решение — паттерн Observer:

```ts
// shared/lib/events — типизированная шина
type DomainEvents = {
  'task:created':   { task: Task }
  'task:completed': { task: Task; pointsAwarded: number }
  'task:cancelled': { task: Task }
  'task:changed':   { task: Task }
  'reward:redeemed':{ balance: number }
  'session:expired': void
  // …
}
```

- Мутации **публикуют** событие.
- Сущности и фичи **подписываются** в своём `setup*()`, который вызывается один раз из `app/providers` (баланс → инвалидирует `points`, звук → играет `TASK_COMPLETED`, статистика → инвалидирует себя).
- Новый потребитель добавляется **без правки** источника (принцип открытости/закрытости).
- Подписки живут в скоупе приложения и снимаются при его разрушении, так что утечек нет.

### 3.6 Ошибки

| Уровень | Что обрабатывает |
|---------|------------------|
| HTTP-клиент | `401` → refresh; превращение ответа в `ApiError` |
| Формы | `VALIDATION` → ошибки под полями (`fieldErrors` из `extension.errors`) |
| Мутации | `CONFLICT`/`OPTIMISTIC_LOCK` → диалог «данные изменились», перечитать |
| Глобально (QueryCache/MutationCache `onError`) | Сетевые, `5xx`, `429` → toast |
| Vue `app.config.errorHandler` + `unhandledrejection` | Непредвиденное → логирование, «что-то пошло не так» |

Тексты для пользователя берутся из словаря `errorCode → сообщение` (`shared/config/error-messages.ts`), иначе — `message` с сервера. Сервер отвечает то по-английски, то по-русски, а словарь даёт единый тон.

## 4. Клиентское состояние (Pinia)

Только setup-stores (`defineStore('x', () => { … })`), маленькие и по одному на ответственность:

| Store | Слайс | Содержит |
|-------|-------|----------|
| `useSessionStore` | `entities/session` | `user`, `status: 'unknown' \| 'authenticated' \| 'guest'`, `logout()` |
| `useThemeStore` | `features/theme-switch` | `'light' \| 'dark' \| 'system'`, сохранение в `localStorage` |
| `useHiddenRewardsStore` | `features/hidden-rewards-unlock` | Пароль **только в памяти**, автоблокировка по таймеру и при уходе вкладки в фон |

Store не вызывает API напрямую для серверных данных — это делает TanStack Query.

## 5. Маршрутизация

| Путь | Страница | Доступ |
|------|----------|--------|
| `/login`, `/register` | Вход, регистрация | Гость |
| `/` → `/today` | Сегодня: планы, сроки, баланс | Вход |
| `/goals`, `/goals/:id` | Цели | Вход |
| `/projects`, `/projects/:id` | Проекты | Вход |
| `/tasks`, `/tasks/:id` | Задачи | Вход |
| `/calendar` | Календарь (`?view=month\|week&date=`) | Вход |
| `/rewards` | Награды и история баллов | Вход |
| `/statistics` | Статистика | Вход |
| `/assistant` | AI-ассистент | Вход |
| `/settings/:section?` | Внешний вид, звуки, рефлексия, скрытые награды | Вход |

- Каждая страница загружается лениво (`() => import(...)`): отдельный чанк.
- `meta: { requiresAuth, guestOnly, layout, title }`. Глобальный guard один раз дожидается `GET /auth/me` при старте.
- Имена маршрутов — константы (`RouteName.TaskDetail`), а не строки в коде.
- Создание и редактирование — в модальном окне или drawer поверх текущей страницы, а не отдельный маршрут. Детальные страницы имеют свой URL, чтобы на них можно было дать ссылку (ссылки из отчёта AI ведут на `/:type/:id`).
- Фильтры и пагинация хранятся в query-параметрах: обновление страницы и кнопка «назад» сохраняют состояние.

## 6. UI-слой

### 6.1 UI-kit (`shared/ui`)

Собственные компоненты, без знания домена:

`AppButton`, `AppIconButton`, `AppInput`, `AppTextarea`, `AppSelect`, `AppCheckbox`, `AppSwitch`, `AppDialog`, `AppDrawer`, `AppConfirm`, `AppToast`, `AppTooltip`, `AppDropdownMenu`, `AppTabs`, `AppBadge`, `AppProgress`, `AppSpinner`, `AppSkeleton`, `AppEmptyState`, `AppDatePicker`, `AppTimePicker`, `AppIcon`.

Правила компонентов:
- `<script setup lang="ts">`, типизированные `defineProps`/`defineEmits`, `defineModel` для v-model.
- Компонент — одна ответственность. Больше ~200 строк — повод разделить.
- Логика, которую можно переиспользовать, выносится в композабл `useXxx`.
- Доступность — с первого дня: фокус, клавиатура, `aria-*`, контраст по токенам.

### 6.2 Где стоит взять библиотеку (решаем вместе перед этапом)

| Задача | Рекомендация | Альтернативы |
|--------|--------------|--------------|
| Dialog, Popover, Dropdown, Select/Combobox, Tooltip — фокус-ловушки, клавиатура, ARIA | **Reka UI** (headless, без стилей — вид полностью наш) | Своё на нативных `<dialog>` + Popover API + Floating UI; Headless UI (мало компонентов) |
| Выбор даты | Calendar/DatePicker из Reka UI | Своё на date-fns |
| Графики статистики | **Свои SVG-компоненты**: столбцы и кольцевая диаграмма, ~0 КБ зависимостей | Chart.js + vue-chartjs (лениво); ECharts — слишком тяжёлый |
| Календарь месяца/недели | Своё: сетка на CSS Grid | FullCalendar — тяжёлый, сложно стилизовать |
| Формы и валидация | **VeeValidate + Valibot** | Regle; свой `useForm` |
| Длинные списки | `@tanstack/vue-virtual` (когда списки реально станут длинными) | — |
| Markdown в ответах AI (если понадобится) | `markdown-it` + `DOMPurify`, лениво | — |

### 6.3 Стили

- Дизайн-токены (`shared/styles/tokens.css`): цвета (семантические: `--color-bg`, `--color-text`, `--color-accent`, `--color-danger` и цвета шести сложностей), типографика, отступы (шаг 4px), радиусы, тени, z-index, длительности анимаций.
- Тёмная тема — переопределение токенов на `[data-theme='dark']`. Компоненты используют только семантические токены и о теме не знают.
- Стиль компонента — в `<style scoped>`. Глобально только reset, токены и типографика.
- Mobile-first, контрольные точки — токенами. Подход к CSS (plain CSS или Tailwind) уточняется перед этапом 1.

## 7. Производительность

### Загрузка
- Ленивые страницы; prefetch вероятного маршрута при наведении или в простое.
- Тяжёлое грузится только там, где нужно: графики — на статистике, markdown — в ассистенте.
- Иконки — `unplugin-icons`: в бандл попадают только используемые SVG как компоненты.
- Шрифт: один variable-шрифт с кириллическим подмножеством, `font-display: swap`, `preload`.
- Сборка под современные браузеры (`es2022`), хешированные имена, долгий кеш, brotli на сервере.
- **Бюджеты** в CI: начальный JS ≤ 150 КБ gzip; LCP < 2 с, INP < 200 мс (Lighthouse CI).

### Рантайм
- Списки — стабильные `:key` по `id`, никогда по индексу.
- `computed` вместо вызова методов в шаблоне; никаких `deep: true` watchers на больших объектах.
- Большие неизменяемые данные — `shallowRef`/`markRaw`. Ответы TanStack Query уже структурно разделяются (неизменившиеся объекты сохраняют ссылку → Vue не перерисовывает).
- `v-memo` — точечно, в доказанно горячих местах (ячейки календаря), а не «на всякий случай».
- Виртуализация — для списков длиннее ~200 элементов.
- `content-visibility: auto` для длинных лент (история баллов, история AI).

### Отсутствие утечек памяти
- Обработчики событий, таймеры, наблюдатели — через **VueUse** (`useEventListener`, `useIntervalFn`, `useResizeObserver`): они снимаются сами при размонтировании. Ручной `addEventListener` без парного удаления — запрещён.
- Композабл с ресурсом обязан освобождать его в `onScopeDispose`.
- Нет модульных (глобальных) массивов, которые растут: кеш — только в TanStack Query с `gcTime`.
- `BroadcastChannel`, `AudioContext` — синглтоны с явным `close()`.
- Напоминания: **один** таймер на ближайшее напоминание, а не по таймеру на задачу.
- `<KeepAlive>` — только с `max`.
- Проверка: сценарий «открыть/закрыть страницу 50 раз» + heap snapshot перед релизом крупных этапов.

## 9. Окружение и деплой

**Проблема:** API отдаёт маршруты из корня (`/tasks`, `/auth/...`), и те же пути — у страниц SPA. Cookie имеют `SameSite=Strict`, refresh-cookie — `Path=/auth`, а клиент ходит с `credentials: 'same-origin'`. Значит, фронт и API должны быть на одном origin, но пути разведены.

Предлагаемое решение (уточняется перед этапом 2):
- Фронт обращается к `/api/*`. Прокси (Vite в разработке, nginx в production) срезает `/api` и **переписывает путь cookie** `/auth` → `/api/auth` (`cookiePathRewrite` в Vite, `proxy_cookie_path` в nginx).
- Бэкенд при этом не меняется. Альтернатива — общий префикс `/api` на самом бэкенде.

Переменные окружения (`.env`, типизированы в `env.d.ts`): `VITE_API_BASE_URL=/api`, `VITE_APP_VERSION`.

## 10. Качество

| Что | Инструмент |
|-----|------------|
| Пакетный менеджер | pnpm, Node LTS (версия в `.nvmrc` и `packageManager`) |
| Типы | `strict`, `noUncheckedIndexedAccess`, `vue-tsc --noEmit` в CI |
| Линт | ESLint (flat config) + `eslint-plugin-vue` + `typescript-eslint` + `eslint-plugin-boundaries` |
| Формат | Prettier |

| Коммиты | Conventional Commits (`feat(tasks): …`) |
| Unit/компоненты | Vitest + @vue/test-utils + happy-dom |
| Моки API | MSW: те же моки работают в тестах и в dev без бэкенда |
| E2E | Playwright: критические сценарии (вход, задача → выполнение → баллы, AI-подтверждение) |

### Что тестируем обязательно
- `shared/api` целиком, особенно refresh между вкладками.
- Мапперы и доменные правила (`*.rules.ts`) — чистые функции, тесты дешёвые.
- Фичи с логикой (формы, подтверждение AI) — компонентными тестами с MSW.
- Простые презентационные компоненты не тестируем ради процента покрытия.

## 11. Соглашения по коду

- Папки и слайсы — `kebab-case`; компоненты — `PascalCase.vue`; композаблы — `useXxx.ts`; типы — `PascalCase` без префикса `I`.
- Брендированные ID: `type TaskId = Brand<string, 'TaskId'>`, чтобы `goalId` нельзя было передать вместо `taskId`.
- Никаких `any`. Неизвестное — `unknown` с сужением.
- Комментарий объясняет **почему**, а не что.
- Публичный API слайса (`index.ts`) экспортирует минимум.
- Каждое отступление от этого документа — либо правка документа, либо ADR.
